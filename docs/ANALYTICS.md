# Аналитика канала

Документ описывает: что реально можно собрать роботом, что — только руками, как это хранится в `state/*.json`, как считается недельный отчёт и как результаты возвращаются обратно в отбор рубрик (SCORE).

> **Статус реализации на 2026-09-20.** Часть описанного уже работает в коде, часть — план развития.
>
> | Блок | Состояние |

> | Запись метаданных поста при публикации (`pipeline/publish.py`) | реализовано |

## 1. Что умеет и чего НЕ умеет Telegram Bot API

Раздел написан по фактическим возможностям Bot API. Всё, что помечено «НЕТ», — не существует в Bot API, и обходится либо MTProto-клиентом (не используем), либо руками.

### 1.1 Что доступно боту-админу канала

| Данные | Как получить | Ограничения |
|---|---|---|
| `message_id` опубликованного поста | Ответ метода `sendMessage` / `sendPhoto` / `sendMediaGroup` (возвращает объект `Message`) | Единственный надёжный источник ID. Сохранять сразу при публикации. |
| Число подписчиков канала | `getChatMemberCount(chat_id)` → целое число | Снимок на момент вызова. Истории нет — историю ведём сами, снимая раз в сутки. |
| Реакции на пост (агрегированные) | Апдейт `message_reaction_count` (объект `MessageReactionCountUpdated`: `chat`, `message_id`, `date`, `reactions: [ReactionCount{type, total_count}]`) | Бот обязан быть **администратором** чата. Апдейт **не** приходит по умолчанию — его нужно явно перечислить в `allowed_updates` при `getUpdates`. Метода «спросить реакции по message_id» (`getMessageReactions`) **не существует** — только поток апдейтов. |
| Реакции с указанием автора | Апдейт `message_reaction` (`MessageReactionUpdated`) | Для каналов реакции анонимны, поэтому на практике приходит именно `message_reaction_count`, а не `message_reaction`. Требует админства и явного `allowed_updates`. |
| Комментарии к посту | Пост автоматически копируется в привязанную группу обсуждений (`is_automatic_forward: true`). Комментарии приходят как обычные `message` в группе с `message_thread_id`, равным `message_id` копии поста в группе. | Нужна привязанная discussion-группа и бот как участник/админ группы. Считаем комментарии сами, инкрементально. Метода «число комментариев к посту» **нет**. |
| Буст-события канала | Апдейты `chat_boost` / `removed_chat_boost`, метод `getUserChatBoosts` | Малоинформативно для нашей задачи, опционально. |
| Клики по CTA | Своя механика: deep-link `https://t.me/<bot_username>?start=<payload>`. Пользователь жмёт кнопку → боту приходит `/start <payload>` | Единственный надёжный способ измерить «дошёл до CTA и нажал». Payload ≤ 64 символа, алфавит `A-Z a-z 0-9 _ -`. |

### 1.2 Чего Bot API НЕ даёт — прямо и без оговорок

* **Просмотры поста (view_count) — НЕТ.** В объекте `Message` Bot API нет поля с просмотрами. Метода получения просмотров нет. Цифра «глазика» под постом видна в приложении Telegram любому читателю, но боту она недоступна.
* **Число пересылок/«шеров» — НЕТ.** Отдельного счётчика пересылок Bot API не отдаёт.
* **Сохранения, переходы по внешним ссылкам, «источники подписчиков» — НЕТ.**
* **Исторические реакции — НЕТ.** Если апдейт `message_reaction_count` не был вычитан, значение не восстановить. `getUpdates` хранит апдейты **до 24 часов** — пропустили окно, данные потеряны навсегда.
* **Список подписчиков — НЕТ** (и не нужен).
* **Статистика канала (графики, ER, источники) — НЕТ.** Это только официальное приложение.

### 1.3 Следствия для архитектуры сбора

1. Workflow опроса апдейтов запускать **не реже, чем раз в 6 часов** (запас к 24-часовому окну хранения). Пропуск суток = безвозвратная потеря реакций. В проекте опрос идёт каждые 30 минут — запас большой.
2. `allowed_updates` при `getUpdates` задавать явно:
   `["message","callback_query","channel_post","message_reaction_count"]`
   Оговорка из документации: параметр не влияет на апдейты, созданные до вызова, поэтому короткое время могут приходить «лишние» типы — игнорировать по типу.
3. `getUpdates` несовместим с установленным webhook. Если webhook когда-либо ставился — снять `deleteWebhook` (это делает `pipeline/approve.py` перед каждым опросом).
4. Один потребитель `getUpdates` на токен. Два параллельных workflow = гонка и потеря апдейтов. Все пишущие workflow объединены в `concurrency: group: pipeline-state, cancel-in-progress: false`.
5. `message_reaction_count` приходит **при изменении**, содержит **абсолютные** тоталы — их просто перезаписываем, а не суммируем.
6. Бот не может написать владелице первым, пока она не нажала Start у бота. Это разовое действие при настройке (шаг 4 в `docs/SETUP.md`).

### 1.4 Что даёт только приложение Telegram (снимается руками)

Встроенная статистика канала («Статистика» в меню канала) доступна при достижении порога по числу подписчиков (Telegram менял порог; исторически — сотни подписчиков). Premium для неё не требуется. Там есть:

* просмотры на пост и средние просмотры;
* динамика подписчиков и **источники подписок** (откуда пришли: ссылка, поиск, репосты);
* «уведомления включены» — доля подписчиков без mute;
* репосты/пересылки по постам;
* топ-посты за период;
* просмотры по источникам.

Плюс — цифра просмотров под каждым постом видна прямо в ленте канала.

**Порядок ручного снятия:** раз в неделю, понедельник, 10:00 Asia/Dubai, по чек-листу из §6. Пока команда `/stats` не реализована, числа вписываются прямо в `state/analytics.json` в блок `metrics` нужного поста (`views`, `forwards`, `comments`) — это единственный путь, которым просмотры и пересылки попадают в отчёт.

### 2.1 Когда какие поля обновляются

| Поле | Кто пишет | Когда |
|---|---|---|
| `message_id`, `published_at`, `rubric`, `source_ids`, `text_len`, `has_cta`, `cta_*`, `has_photo`, `media_count`, `score_at_selection`, `rubric_weight_at_selection`, `approved_first_try`, `factcheck_rejections` | publish-workflow | один раз, в момент публикации, больше не меняются |
| `thread_root_message_id` | poll-workflow | при получении автопересылки поста в группу обсуждений (`is_automatic_forward`) |
| `reactions_*` | poll-workflow | при каждом апдейте `message_reaction_count` (перезапись абсолютных значений) |
| `comments` | poll-workflow | инкремент при каждом сообщении в группе с соответствующим `message_thread_id`; сообщения самого бота и автопересылка не считаются |
| `cta_clicks` | poll-workflow | инкремент при `/start <payload>`; повторный `/start` от того же `user_id` по тому же payload — не считаем (дедупликация по хэшу `user_id+payload`, сам `user_id` не хранится) |
| `leads_attributed` | leads-workflow | при создании/квалификации лида с этим `post_id` |
| `views_manual`, `forwards_manual` | ручной ввод владелицы | раз в неделю |
| `derived.*` | report-workflow | пересчёт перед формированием отчёта |
| `channel.subscribers[]` | daily-workflow | раз в сутки |

`collection_status`: `pending` (нет ручных данных и прошло <7 дней) → `api_only` (есть апи-метрики, ручных нет) → `complete` (заполнены просмотры). Посты старше 30 дней метриками не обновляются: `frozen`.

**Ротация:** посты старше 180 дней сворачиваются в месячные агрегаты `archive.months[]`, детальные записи удаляются, чтобы файл не рос бесконечно. `collection_log` — последние 50 записей.

## 3. Схема `state/leads.json` — без персональных данных

**Правило:** в репозитории — только счётчики и обезличенные записи. Никаких имён, телефонов, @username, e-mail, ссылок на профиль, текста переписки, бюджета в связке с человеком.

```json
{
  "version": 1,
  "updated_at": "2026-09-20T18:05:00+04:00",
  "counters": {
    "total": 41,
    "by_month": {
      "2026-08": { "new": 12, "qualified": 7, "meeting": 3, "deal": 1, "lost": 4 },
      "2026-09": { "new": 9, "qualified": 5, "meeting": 2, "deal": 0, "lost": 1 }
    },
    "by_launch": { "emaar-grand-club": 14, "damac-islands-2": 9, "unspecified": 18 },
    "by_rubric": { "new_launch": 19, "investor_math": 11, "case_story": 6, "faq_answer": 3, "market_pulse": 2 },
    "by_channel": { "bot_deeplink": 27, "dm_direct": 9, "comment": 5 }
  },
  "leads": [
    {
      "lead_id": "7f3a91c0e4d25b18",
      "created_date": "2026-09-18",
      "launch_id": "emaar-grand-club",
      "rubric": "new_launch",
      "post_id": "2026-09-18-new_launch-emaar-grand-club",
      "cta_payload": "p_a1b2c3d4",
      "channel": "bot_deeplink",
      "status": "qualified",
      "status_updated_date": "2026-09-19",
      "budget_band": "1-2m_aed",
      "notes_code": "invest_yield"
    }

```

Допустимые значения:
* `channel`: `bot_deeplink` | `dm_direct` | `comment` | `referral` | `offline` | `unknown`
* `status`: `new` | `qualified` | `meeting` | `deal` | `lost`
* `budget_band`: `lt_1m_aed` | `1-2m_aed` | `2-5m_aed` | `gt_5m_aed` | `unknown` — **только диапазон**, не точная сумма
* `notes_code`: справочник из 10–15 кодов мотива (`invest_yield`, `golden_visa`, `relocation`, `flip`, `school_area`, …). Свободного текста нет — он утечёт как персональные данные.

### 3.1 Как получается `lead_id`

`lead_id = sha256(LEAD_HASH_SALT + "|" + normalized_contact)[:16]`, где `LEAD_HASH_SALT` — GitHub Secret длиной не меньше 32 байт, **никогда** не попадающий в репозиторий, а `normalized_contact` — телефон в формате E.164 или `tg:<user_id>`.

Честное предупреждение: хэш телефона без секретной соли подбирается перебором за минуты (пространство номеров мало). Поэтому соль обязательна, секретна и не ротируется без пересчёта (при ротации старые `lead_id` становятся несопоставимыми — фиксируем `salt_version` в файле, если придётся менять). Хэш — это **псевдонимизация, а не анонимизация**: по запросу на удаление данных запись из `leads[]` тоже удаляется, а счётчики уменьшаются.

### 3.2 Где хранятся контакты

Вне репозитория, в одном из:
* CRM брокера (предпочтительно) — там же история сделок;
* приватная Google-таблица с доступом «только владелица», 2FA включена;
* приватный (не публичный!) отдельный репозиторий — худший вариант, допустим только временно.

Связка: в CRM есть колонка `lead_id` с тем же хэшем. Репозиторий отвечает за «сколько и откуда», CRM — за «кто». Ни один workflow не имеет доступа к CRM.

**Почему так:** публичный репозиторий индексируется, форкается и кэшируется; удалить данные из истории git и из чужих форков невозможно. Одна утечка номера клиента — это репутационный и правовой инцидент (см. `docs/LEGAL.md`).

## 4. Недельный отчёт

### 4.1 Период и запуск

Окно: понедельник 00:00 — воскресенье 23:59 Asia/Dubai. Отчёт формируется в понедельник утром (`.github/workflows/analytics-weekly.yml`, cron `0 4 * * 1` UTC = 08:00 Дубай). Если ручных цифр нет, отчёт всё равно уходит, но блок просмотров помечается «нет данных».

### 4.2 Формулы

**ER по просмотрам (основной, требует ручных данных):**

```
ER_views = (реакции + комментарии + пересылки) / просмотры × 100%
```

**ER по подписчикам (ERS, считается автоматически, доступен всегда):**

```
ERS = (реакции + комментарии) / подписчики_на_дату_публикации × 100%
```

ERS — рабочий прокси, когда просмотров нет. Сравнивать ERS и ER_views между собой нельзя, это разные шкалы; в отчёте они идут отдельными строками.

**Охват поста:**
```
Reach% = просмотры / подписчики_на_дату_публикации × 100%
```

**CTR CTA:**
```
CTR = cta_clicks / просмотры × 100%      (если просмотров нет: cta_clicks / подписчики)
```

**Конверсия клика в заявку:**
```
CR_click→lead = leads_attributed / cta_clicks × 100%
```

**Конверсия поста в заявку:**
```
CR_post = leads_attributed / просмотры × 100%
```

**Прирост подписчиков:**
```
Growth% = (подписчики_конец − подписчики_начало) / подписчики_начало × 100%
Net_new = подписчики_конец − подписчики_начало   (нетто, отписки уже вычтены)
```

### 4.3 Сравнение рубрик при разном числе постов

Прямое сравнение средних некорректно: у `personal` за неделю 1 пост, у `market_pulse` — 3. Используем сглаживание к среднему по каналу (эмпирический байес):

```
adj_metric(r) = (Σ metric по постам рубрики r + k × μ) / (n_r + k)
```

где `μ` — среднее значение метрики по всем постам окна расчёта, `k = 3` (эквивалент «трёх воображаемых средних постов»).

Правила отображения:
* `n_r = 0` → рубрика в таблице не показывается;
* `n_r ∈ {1,2}` → показывается с пометкой «мало данных, n=…», в выводы и в SCORE не идёт;
* `n_r ≥ 3` → полноценно.

Индекс рубрики для отчёта: `Index(r) = adj_metric(r) / μ`. Значение 1.00 = «как в среднем по каналу», 1.30 = «на 30% лучше среднего».

Окно для рубричных выводов — **28 дней**, а не 7: за неделю по рубрике физически не набирается выборка. Недельный отчёт показывает недельные абсолюты, но рубричный рейтинг — всегда скользящие 28 дней.

### 4.4 Целевой шаблон текста отчёта

Отправляется в личку владелице, `parse_mode=HTML`, все подставляемые значения экранируются. Плейсхолдеры в фигурных скобках.

```
<b>Отчёт за неделю {week_label}</b>
{date_from} — {date_to}

<b>Главное</b>
Заявки на лончи: <b>{leads_week}</b> (прошлая неделя: {leads_prev}, {leads_delta_sign}{leads_delta})
За месяц накопительно: <b>{leads_month}</b> из цели {leads_goal}
Квалифицированные: {leads_qualified} · Встречи: {leads_meeting}

<b>Канал</b>
Подписчиков: <b>{subs_end}</b> ({subs_delta_sign}{subs_delta} за неделю, {growth_pct}%)
Постов опубликовано: {posts_count}
Средние просмотры на пост: {avg_views}
Средний охват: {avg_reach_pct}% от подписчиков
ER по просмотрам: <b>{er_views_pct}%</b>
ER по подписчикам: {ers_pct}%

<b>Воронка CTA</b>
Постов с CTA: {posts_with_cta} из {posts_count} ({cta_share_pct}%)

CTR: {ctr_pct}% · Клик → заявка: {cr_click_lead_pct}%
Пост → заявка: {cr_post_pct}%

<b>Топ-3 поста недели</b>
```

## 5. Обратная связь в SCORE: как результаты меняют веса рубрик

### 5.1 Что считаем

Для каждой рубрики `r` в окне 28 дней:

```
L(r) = adj( leads_attributed на пост )      — заявки
E(r) = adj( ERS на пост )                   — вовлечение
```
`adj()` — сглаживание из §4.3 с `k = 3`.

Индексы: `L_idx(r) = L(r)/μ_L`, `E_idx(r) = E(r)/μ_E`.

Итоговая результативность (заявки весят больше, это главная метрика владельца):

```
P(r) = 0.65 × L_idx(r) + 0.35 × E_idx(r)
```

### 5.2 Обновление веса

```
m(r)      = clamp( 1 + λ × (P(r) − 1), 0.85, 1.20 )        λ = 0.5
w_target  = w_current(r) × m(r)
w_new(r)  = 0.7 × w_current(r) + 0.3 × w_target            (EMA-сглаживание)
w_new(r)  = clamp( w_new(r), 0.5 × w_base(r), 1.8 × w_base(r) )
```

Затем нормировка: `w_new(r) ← w_new(r) × (Σ w_base / Σ w_new)` — сумма весов сохраняется, чтобы не менялась общая частота публикаций.

`w_base(r)` — базовый вес из конфига контент-плана, он не меняется никогда; дрейф считается только относительно него.

> Текущая реализация в `pipeline/analytics.py` проще: она двигает вес к отношению
> `ER рубрики / средний ER` с коэффициентом 0.25 и зажимает результат в коридор
> `[0.6, 1.6]`, а при выборке меньше трёх постов не трогает вес вообще.
> Формула выше — целевая; переход на неё требует данных по заявкам (`leads_attributed`).

### 5.3 Ограничения и защиты

| Защита | Правило |
|---|---|
| Малая выборка | `n_r < 4` постов в окне → `m(r) = 1.0`, вес не меняется |
| Пограничная выборка | `n_r ∈ {4,5}` → `λ = 0.25` вместо 0.5 |
| Максимальный шаг | ±20% за один пересчёт |
| Максимальный дрейф | коридор `[0.5·w_base, 1.8·w_base]` — рубрика не может исчезнуть и не может захватить ленту |
| Неприкосновенный минимум | `rules_and_laws` и `market_pulse` не ниже `0.7·w_base` (доверие и экспертность важнее недельного ER); `new_launch` не ниже `0.8·w_base` (это источник заявок) |
| Потолок «лёгкого» контента | `personal`, `dubai_life`, `events_afisha` — не выше `1.2·w_base`: они легко собирают реакции, но не дают заявок, и без потолка съедят план |
| Потолок продающего | суммарная доля `new_launch + investor_math + case_story` после нормировки не выше 0.25; при превышении излишек пропорционально возвращается остальным |
| Сезонность | если в окне был отпуск или пауза больше 7 дней — пересчёт пропускается |
| Аудит | каждое изменение пишется в историю весов: дата, рубрика, `w_old`, `w_new`, `P(r)`, `n_r`. Ручной откат — редактированием файла |

### 5.4 Период пересчёта

Первый понедельник месяца, после недельного отчёта. Чаще нельзя: 28-дневное окно и месячный шаг гарантируют, что выборка обновилась хотя бы наполовину. Первые 8 недель жизни канала пересчёт **не выполняется вообще** — данных нет, любые веса будут шумом.

Бот прикладывает к отчёту сводку изменений:

```
Пересчёт весов рубрик ({window_from}—{window_to})
new_launch     1.00 → 1.14  (P=1.42, n=7)
investor_math  1.00 → 1.06  (P=1.17, n=5)
dubai_life     1.00 → 0.93  (P=0.71, n=6)
area_guide     без изменений (n=2, мало данных)
```

## 6. Ручные метрики: недельный чек-лист владельца

Раз в неделю, понедельник около 10:00 Asia/Dubai, 5–7 минут. Открыть канал → «Статистика».

1. **Средние просмотры на пост за неделю** — из графика «Просмотры» или вручную по «глазику» под последними постами.
2. **Просмотры по каждому посту недели** — число под постом; нужны для рубричного сравнения.
3. **Пересылки (репосты) за неделю** — блок «Репосты» в статистике, суммарно.
4. **Доля подписчиков с включёнными уведомлениями** — показатель «здоровья» аудитории; падение ниже 60% = усталость от контента.
5. **Отписки за неделю** — по графику подписчиков; важно в связке с продающими постами.
6. **Источники новых подписчиков** — топ-2 источника словами (ссылка из сторис, репосты, поиск).
7. **Топ-пост недели по просмотрам** — `message_id` или первые слова.

Куда вписывать: пока команда `/stats` не реализована — прямо в `state/analytics.json`,
в блок `metrics` соответствующего поста (`views`, `forwards`, `comments`) и в
`weekly[]`. Правило валидации: только целые числа и проценты 0–100; отклонение
больше чем в 5 раз от прошлой недели — повод перепроверить, а не вписывать.
