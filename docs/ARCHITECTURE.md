# Архитектура

Документ для того, кто будет чинить или развивать пайплайн. Пошаговая инструкция
по запуску — в [SETUP.md](SETUP.md).

## Общая идея

Нет сервера. Нет базы данных. Есть репозиторий и GitHub Actions.

- **Кодом** является содержимое `pipeline/`.
- **Базой данных** является папка `state/` — обычные JSON-файлы, которые бот
  коммитит обратно в репозиторий. Это бесплатно, даёт полную историю изменений
  и аудит: видно, какой пост когда сгенерирован, кем одобрен и когда опубликован.
- **Планировщиком** является cron в GitHub Actions. Все cron задаются в UTC,
  а аудитория живёт по Asia/Dubai (UTC+4) — поэтому в каждом workflow
  над расписанием стоит комментарий с пересчётом.

## Контур

```
[1 COLLECT]     pipeline/collect.py      config/sources.yml → сырые items
      │
[2 NORMALIZE]   pipeline/normalize.py    единая схема + дедупликация → state/seen_items.json
      │
[3 SCORE]       pipeline/score.py        свежесть × вес источника × ключевые слова
      │
[4 GENERATE]    pipeline/generate.py     промпт из prompts/ → LLM → JSON
      │         pipeline/llm.py          провайдер: anthropic | openai | offline
      │         pipeline/factcheck.py    факт-чек-гейт: брак не проходит дальше
      │
[5 ILLUSTRATE]  pipeline/illustrate.py   фото-карточка: пресс-фото → gpt-image-1 → сток → градиент
      │
[6 QUEUE]       pipeline/postqueue.py    слот публикации → state/queue.json
      │
[7 APPROVE]     pipeline/approve.py      превью владельцу + getUpdates long-poll
      │                                  → state/telegram_offset.json
      │                                  материалы владельца → state/inbox.json
      │         pipeline/inbox.py        копилка → понимание → черновик (→ [4]…[6])
[8 PUBLISH]     pipeline/publish.py      идемпотентная отправка → state/published.json
      │
[9 ANALYTICS]   pipeline/analytics.py    недельный отчёт → state/analytics.json
                                         пересчёт весов → state/rubric_weights.json
                                                    │
                                                    └──→ обратно в [3 SCORE]
```

## Ключевые решения и почему так

### Состояние в репозитории

GitHub Actions stateless: между запусками на раннере не остаётся ничего.
Варианты были: внешняя БД (стоит денег и добавляет точку отказа), артефакты
Actions (живут 90 дней, неудобно читать), репозиторий (бесплатно, версионируется).
Выбран репозиторий. Запись атомарная (`tempfile` + `os.replace`), чтобы
прерванный прогон не оставил половину файла.

Все workflow, которые пишут в `state/`, помечены
`concurrency: group: pipeline-state` — это не даёт двум прогонам одновременно
переписывать одни и те же файлы. `scripts/commit_state.sh` дополнительно
повторяет push с `git pull --rebase`, если ветка успела уйти вперёд.

### Апрув через getUpdates, а не webhook

Webhook требует постоянно доступного HTTPS-эндпоинта — его нет. Поэтому короткий
workflow периодически делает long-poll `getUpdates`.

Два следствия, которые учтены в коде:
1. `getUpdates` и webhook взаимоисключающи. Перед опросом `approve.run()`
   вызывает `deleteWebhook`.
2. Offset надо персистить, иначе одно и то же нажатие обработается дважды.
   Он лежит в `state/telegram_offset.json`.

Нажатия принимаются только от `TELEGRAM_OWNER_ID`. Кнопка от кого-то другого
игнорируется, пользователь получает «Недостаточно прав».

### Идемпотентность публикации

`publish_key = sha1(post_id + slot_at)`. Ключ **записывается в
`state/published.json` и файл сохраняется на диск ДО обращения к Telegram**.
Если прогон упадёт между записью и отправкой, пост будет пропущен (отказ
в безопасную сторону), а не отправлен дважды. Если отправка упала с ошибкой,
ключ освобождается — следующий прогон повторит.

Повторный запуск workflow `Publish` на том же слоте просто ничего не делает.

### Лимиты Telegram

Подпись к фото — 1024 символа, обычное сообщение — 4096.
`textutil.plan_delivery()` выбирает режим:

| Условие | Режим | Что уходит |
|---|---|---|
| фото есть, текст ≤ 1024 | `photo` | одно сообщение с подписью |
| фото есть, текст > 1024 | `photo_plus_text` | фото с короткой подписью + остаток отдельными сообщениями |
| фото нет | `text` | текст, нарезанный по 4096 по границам абзацев |

Нарезка идёт по `\n\n`, затем по `\n`, затем по пробелу, затем жёстко —
функция всегда завершается и никогда не возвращает кусок длиннее лимита.

### Анти-галлюцинации

`pipeline/factcheck.py` — гейт между GENERATE и QUEUE. Пост не проходит, если:

- в тексте есть число, которого нет ни во входных материалах, ни в блоке `facts`;
- процитирован URL, которого не было во входных материалах;
- есть запрещённая инвестиционная формулировка («гарантированная доходность» и т.п.);
- текст не на русском;
- длина превышает лимит Telegram;
- сама модель выставила `false` любому флагу в `self_check`.

При провале делается вторая попытка: тот же промпт плюс список претензий гейта.
Если и она не прошла — пост помечается `failed` и в очередь не попадает.

### Истории вместо материалов (SCORE → GENERATE)

Восемнадцать источников — Telegram-каналы, которые пересказывают одну и ту
же новость своими словами в течение нескольких часов. `normalize.dedupe`
ловит только совпадение canonical URL или байтово одинаковый заголовок, так
что пересказы доходили до SCORE как разные материалы, и модель получала
четыре случайных версии одной новости.

`pipeline/stories.py` группирует материалы в **истории** без внешних
библиотек и без LLM:

1. текст `title + summary` приводится к нижнему регистру, чистится от
   пунктуации и стоп-слов RU/EN, слова грубо стеммятся (обрезка до 5–6
   символов);
2. токены взвешиваются: именованные сущности (слова с заглавной буквы в
   оригинале, латинские названия — Emaar, DEWA, RTA) ×3, числа ×2, остальное ×1;
   «Dubai», «ОАЭ» и подобные сущностями не считаются, иначе они склеили бы всё;
3. два материала — одна история, если взвешенный Жаккар их множеств ≥ 0,3
   и между датами публикации не больше 72 часов;
4. **конфликт имён** запрещает склейку при любой похожести: если у каждого
   из двух материалов есть ≥ 2 имени собственных (слова с заглавной не в
   начале предложения, кроме «Dubai», «ОАЭ» и т. п.), которых нет у другого,
   это разные истории. Иначе «Emaar запустил Park Lane 2 в Dubai Hills» и
   «Emaar запустил Golf Grand 3 в Dubai Hills» — один шаблон канала, один
   застройщик, один район — склеивались с похожестью 0,59, выше, чем у
   русского и английского пересказа одного лонча (`stories.proper_names`,
   `names_conflict`);
5. объединение жадное и детерминированное: материалы обходятся в порядке
   убывания score, каждый присоединяется к истории с самым похожим членом
   (single linkage) либо начинает новую.

`Story.score = лучший score материала × (1 + 0,15 × (число независимых
источников − 1))`, потолок ×1,6. Новость, о которой пишут пять каналов,
важнее новости из одного.

Отбор в `score.select_for_rubric` идёт по историям: `plan_rubrics` ранжирует
рубрики по score ведущей истории, а в промпт уходят **все** материалы ведущей
истории (до 6, лучшие по score, строго по одному на источник) плюс до 2
материалов из других историй, если позволяет `ITEMS_PER_POST`. `generate()`
кластеризует один раз на прогон и не отдаёт одну историю двум рубрикам.
В логе: «Историй: N из M материалов; крупнейшие: …».

Исключение — **рубрики-дайджесты** (`RUBRICS[r]["digest"]`, сейчас только
`events_afisha`): афише нужны 3–5 разных событий, а не пять пересказов одного
концерта. Для них `select_for_rubric` отдаёт по одному лучшему материалу из
каждой из лучших историй (до `DIGEST_STORIES = 6`), а `generate()` помечает
использованными все эти истории, а не только ведущую (`score.stories_used`).

### Уверенность в фактах

Каждый факт в `facts[]` ответа модели несёт `confidence` и `sources`
(правила — раздел «Проверка и маркировка» в `prompts/system_tone.md`):

| Уровень | Когда | Как звучит в тексте |
|---|---|---|
| `confirmed` | официальный источник (`official_data`, `developers`, `city_gov` не из Telegram), собственная заметка или фото владелицы (`owner_inbox` с тегом `note`, не `forward`/`screenshot`) или ≥2 независимых `source_id` | утверждение |
| `single_source` | один Telegram-канал или одно СМИ | «по данным …, официального подтверждения пока нет» |
| `rumour` | источник сам подаёт как слух/ожидание | «по слухам / ожидается / возможно» в том же предложении, что и цифра |

`factcheck.check_confidence` сверяет уровень с входными материалами:
`confirmed` без двух независимых url (или одного официального) понижается до
`single_source` с предупреждением; для `single_source` в тексте обязан быть
маркер неуверенности (регулярка `HEDGE_RE`), иначе ошибка гейта; цифра из
`rumour` не может стоять в предложении без «слух/ожидается/возможно». Поля
необязательны — старые ответы и офлайн-заглушка проходят с предупреждением.
Категорию источника гейт берёт из `NormalizedItem.category`, тип
(Telegram или нет) — из `config/sources.yml`, который читается один раз.

### Защита от prompt injection

Текст из RSS попадает в промпт модели, то есть третья сторона может попытаться
управлять ботом. Меры:

1. `normalize.scrub_untrusted()` вырезает инструкционные маркеры
   («ignore previous instructions», «системный промпт» и т.п.) ещё на входе.
2. Входные материалы подаются в промпт как JSON внутри тега `<INPUT_ITEMS>`,
   то есть как данные, а не как указания.
3. Ответ модели проходит `sanitize_telegram_html()` — остаются только теги,
   которые Telegram вообще принимает.
4. Факт-чек-гейт не даёт опубликовать ссылку, которой не было во входных данных.
5. Финальный барьер — ручной апрув: ни один пост не уходит в канал без нажатия
   кнопки владельцем.

Подробнее — в [SECURITY.md](SECURITY.md).

### Статья по ссылке (обогащение перед генерацией)

Пост из Telegram-канала — это два предложения; другой канал написал
«прикольный» пост о той же новости, потому что его автор прочитал
первоисточник (масштаб, цифры, кто управляет). `pipeline/enrich.py` перед
генерацией берёт для каждого материала пула первую внешнюю ссылку из текста
поста (не t.me, не соцсети) либо саму страницу материала, если фид отдал
только тизер, скачивает её и добавляет читаемый текст статьи (абзацы и
заголовки, до 3500 символов) в `summary` материала с пометкой «Статья по
ссылке». Не больше шести загрузок на пул, кэш в памяти, в DRY_RUN сети нет.
Факт-чек-гейт по-прежнему требует, чтобы каждая цифра была во входных
данных — теперь они там есть. То же делается при переписывании поста
(`run.regenerate_rewrites`), поэтому снимок `source_items` хранит до 3000
символов `summary`. Пул рубрики — только материалы ведущей истории
(`EXTRA_STORY_ITEMS = 0`): «контекст» из чужих историй оказался шумом.

### Изображения

Формат по умолчанию — **светлая компактная карточка** (`card.style: light`
в `assets/brand.yml`): 1200×630, кремовый фон, два едва заметных цветных
пятна, слева сверху пилюли «ДУБАЙ» и тег рубрики, справа сверху вордмарк,
тёмно-синий заголовок до 3 строк (кегль подбирается, пока заголовок,
золотая полоска и строка-акцент не уместятся над нижним полем), под ним
золотая полоска и цифра-акцент. Ни фото, ни стоков, ни ИИ — бесплатно и
без тёмных блоков; в ленте занимает треть высоты вертикальной 4:5.
Владелец попросил именно так: «компактнее, светлые квадраты, без расходов».
`image_meta.background = "light"`, `ensure_image` перерисовывает её при
потере файла. Палитра — блок `light:` в `brand.yml`, тёмный логотип для
светлого фона — `light.logo_path`.

Для рубрики `meme` тот же светлый лист несёт **текстовый мем**
(`render_meme_card`): макеты «Никто / Абсолютно никто / Дубай», «Ожидание /
Реальность», «Я / Тоже я» и «подводка + панчлайн». Модель отдаёт макет и
строки в `image.meme` (см. prompts/meme.md), код кладёт их на карточку
дословно; спецификация сохраняется в `image_meta.meme` для перерисовки.

Запасной формат — «фото-карточка» (ориентир — каналы Whitewill и Ruble,
включается `card.style: photo` или `editorial`): фотография
на весь кадр с cover-кропом, мягкое затемнение сверху и снизу, заголовок
жирным гротеском заглавными слева сверху (автоперенос до 4 строк, кегль
подбирается автоматически, длинные русские слова переносятся по дефису или
по буквам), вордмарк или `assets/logo.png` справа сверху, внизу слева
одна-две пилюли: место («ДУБАЙ», «АБУ-ДАБИ» — по ключевым словам поста) и тег
рубрики («#НОВОСТЬДНЯ», «#ЛОТНЕДЕЛИ» — маппинг в `assets/brand.yml`).
Опциональная цифра-акцент золотым под заголовком. Размер по умолчанию
1080×1350 (4:5), допустим 1200×675 (16:9). Второй стиль `editorial`
(Ruble-подобный: сериф по центру внизу, фото затемнено, пилюля-обводка).

Откуда берётся фотография — цепочка приоритетов в `illustrate()`,
результат виден в `image_meta.provider` и в логе:

1. `press` — собственное фото источника (`source_items[*].image_url`), только
   если источник в `config/sources.yml` помечен `license.reuse: press_release`,
   относится к категории `developers` / `official_data` / `city_gov` и не
   является чужим каналом (`role: signal`). Скачивается в `assets/cache/`
   (таймаут 20 с, до 5 МБ, короткая сторона ≥ 600 px).
2. `generated` — OpenAI `gpt-image-1` (1024×1536 для 4:5, 1536×1024 для 16:9),
   промпт = `image.stock_query` + стилевой хвост из `brand.yml`. Только при
   `OPENAI_API_KEY`; для рубрик про конкретный объект (`new_launch`,
   `case_story`) пропускается — [LEGAL.md](LEGAL.md) запрещает выдавать
   ИИ-картинку за фото реального проекта; в `image_meta` пометка «иллюстрация».
   Вызов изолирован в `generate_image(settings, prompt)`, чтобы тесты и другие
   провайдеры могли его подменить.
3. `unsplash` / `pexels` — сток по английским ключевым словам модели
   (`fetch_stock`), ориентация под формат карточки.
4. `own_card` — та же раскладка поверх фирменного градиента (без фото).

В DRY_RUN сеть не трогается вовсе: карточка рисуется поверх синтетического
фона «небо — море — башни» (`render_synthetic_photo`), чтобы превью выглядело
осмысленно. По каждой картинке фиксируются автор, лицензия и URL источника
(`image_meta`), это требование [LEGAL.md](LEGAL.md).

`ensure_image` восстанавливает картинку, если файл потерян между запусками
(assets/generated/ не коммитится): для `press` / `unsplash` / `pexels` —
повторное скачивание по `image_meta.remote_url`, для `generated` — без
повторной генерации (платно), пост получает градиентную карточку с пометкой
в `image_meta.note`.

Шрифт: `brand.yml → assets/fonts/*.ttf → системный DejaVu Sans Bold` (есть на
ubuntu-раннерах GitHub, поддерживает кириллицу). Цвета, вордмарк, путь к
логотипу, теги рубрик, размеры и радиусы настраиваются в `assets/brand.yml`
без правки кода.

### Слой LLM

`pipeline/llm.py` — протокол `LLMProvider` с тремя реализациями:

- `AnthropicProvider` — основной, модель по умолчанию `claude-opus-5`
  (переопределяется переменной `LLM_MODEL`);
- `OpenAIProvider` — тот же интерфейс, включается `LLM_PROVIDER=openai`;
- `OfflineProvider` — используется в `DRY_RUN` и в тестах, строит корректный
  по схеме ответ из самого промпта и **не делает ни одного сетевого вызова**.

У обоих сетевых провайдеров — 4 попытки с экспоненциальной паузой.

Промпты не захардкожены: `pipeline/prompts.py` грузит `prompts/system_tone.md`
и `prompts/<rubric_id>.md`. Добавить рубрику = добавить файл промпта и запись
в `RUBRICS` в `pipeline/config.py`. Тест `tests/test_prompts_rubrics.py` следит,
чтобы код, промпты и `docs/RUBRICS.md` не разъехались.

### Копилка владельца

Владелица пересылает боту в личку скриншоты постов и сторис из Instagram,
рилсы, PDF застройщиков (прайсы, планировки, планы оплаты), пересланные
посты из WhatsApp и Telegram, свои заметки. `approve._store_owner_material`
складывает всё это в `state/inbox.json` (текст/подпись, `photo_file_id`,
`document{file_id,name,mime}`, `origin`). Дальше работает `pipeline/inbox.py`.

Путь материала от пересылки до превью:

```
пересылка боту ──(approve poll, ≤30 мин)──► state/inbox.json
      │
      ▼  pipeline.run --stage inbox  (после каждого poll и в начале generate)
[понимание]  getFile + скачивание в assets/cache/inbox/ (не коммитится)
      фото/скриншот ─► Claude vision: текст дословно + описание + kind
                       (screenshot | floorplan | pricelist | photo | other)
      PDF ───────────► pypdf; если текста < 200 симв. (скан) — картинки
                       страниц через pypdf → vision; иначе needs_ocr
      видео ─────────► ffmpeg → mp3 → OpenAI Whisper (whisper-1),
                       только если задан OPENAI_API_KEY; иначе
                       needs_openai_key и пост строится по подписи
      → entry.extracted = {text, description, kind, transcript, method, error}
      → entry.processed_at
      │
[черновик]   entry → NormalizedItem(source_id=owner_inbox, category=lifestyle,
             url=https://t.me/c/inbox/<message_id> или ссылка на пост канала)
             → generate.generate_for_rubric("from_owner") — тот же промпт-
               конвейер, тот же факт-чек-гейт, что и у новостей
             → postqueue.enqueue → entry.drafted_at, entry.post_id
             → превью владелице сразу (stage inbox) или ближайшим approve
      модель вернула skip → entry.skipped_reason + сообщение владелице
```

Решения, которые стоит знать, прежде чем править:

- **Идемпотентность.** Обработанные элементы (`processed_at`) не читаются
  повторно, превращённые в черновик (`drafted_at`) и пропущенные
  (`skipped_reason`) не генерируются снова. На пустой копилке стадия
  выходит до создания провайдера и Telegram-клиента — ни одного ключа не
  нужно, минуты Actions не тратятся.
- **Skip и сбой — разные вещи.** Провайдер оборачивается в `_Recording`,
  который помнит последний сырой ответ: если модель вернула `skip`,
  элемент паркуется сразу с её `skip_reason`; если ответа нет
  (сеть, обрезанный JSON), элемент получит вторую попытку в следующем
  прогоне (`MAX_DRAFT_ATTEMPTS = 2`) и только потом паркуется.
- **Картинка поста.** Фото владельца (планировка, прайс, её снимок)
  становится изображением поста через Telegram `file_id`
  (`queue.posts[].telegram_file_id`) — approve и publish не зависят от
  `assets/cache/`, который между запусками не живёт. Скриншот чужого поста
  (`kind: screenshot`) картинкой не становится — рисуется карточка,
  см. LEGAL.md. Перечень — `OWNER_PHOTO_KINDS`.
- **Пересылки из собственного канала** (username совпадает с
  `TELEGRAM_CHANNEL_ID`) — это образцы голоса для `voice_samples`, они
  помечаются пропущенными без обращения к модели.
- **Размер состояния.** `extracted.text` и `transcript` — не более 6000
  символов, `description` — 1000; файлы Bot API отдаёт только до 20 МБ
  (`too_large`): лимит проверяется по `file_size` из `getFile` до скачивания
  и по потоку во время (`TelegramClient.MAX_DOWNLOAD_BYTES`), обрезанный
  файл удаляется. Имя файла в кеше — хэш `file_id` плюс расширение только
  вида `.jpg`/`.pdf` (`inbox.cache_path`), ничего из `file_path` Telegram в
  путь не попадает.
- **Токен бота не попадает в состояние.** `requests` кладёт URL запроса —
  с `/bot<TOKEN>/` — в текст исключения; `TelegramClient` вырезает токен
  из ошибок ещё до того, как они станут `TelegramError`, потому что
  `extracted.error` пишется в `state/inbox.json` и коммитится. Лог-редактор
  (`logging_setup`) — второй рубеж, но он защищает только лог.
- **Картинка для vision.** `media_type` определяется по магическим байтам,
  а не по расширению (PNG под именем `.jpg` API отверг бы); файлы больше
  4,5 МБ, длиннее 2000 px по длинной стороне или неизвестного формата
  перекодируются в JPEG (`inbox._prepare_image`).
- **Порядок записи.** Сначала сохраняется `queue.json`, потом `inbox.json`
  с `drafted_at`. Сбой между ними означает повторную генерацию в следующем
  прогоне — `post_id` выводится из `message_id`, и `enqueue` обновит ту же
  запись, а не создаст дубль. Обратный порядок терял бы материал навсегда.
- **Пост из копилки — через общий `generate_for_rubric`**, поэтому все
  анти-галлюцинационные правила действуют: цифра в посте обязана быть в
  `summary` материала (туда попадают подпись, текст с картинки, PDF и
  расшифровка). Кнопка «Переписать» работает по `source_items`, где
  `summary` обрезан до 600 символов, — переписанный пост из длинного PDF
  может потерять часть фактуры; это ограничение `generate.snapshot_items`.

### Изображения: что проверяется у чужих файлов

Пресс-фото и сток скачиваются потоком с потолком 5 МБ (заявленный
`Content-Length` и фактический объём, `illustrate._fetch_bounded`), затем
проверяются Pillow по заголовку: не картинка, короткая сторона меньше 600 px
(пресс) или больше `PHOTO_MAX_PIXELS` = 30 Мп — файл удаляется, цепочка идёт
дальше. Сгенерированная gpt-image картинка кешируется по хэшу промпта
(`assets/cache/gen-<hash>.png`): «Переписать» в том же прогоне или повтор на
том же раннере не платит за неё второй раз; между запусками кеш не живёт, и
переписанный пост (новый заголовок на карточке) генерирует фон заново —
не больше `MAX_REWRITES = 3` раз на пост. При отсутствии сети или 404 при
перекачке `ensure_image` рисует градиентную карточку, а не падает.

### Сухой прогон

`DRY_RUN=1` (или `--dry-run`) меняет три вещи:
- COLLECT читает `config/sample_items.json` вместо сети;
- LLM-провайдер становится офлайновым;
- `TelegramClient` не открывает сокет, а записывает вызов в `self.calls`.

Тест `tests/test_dry_run_no_network.py` подменяет `socket.socket` на функцию,
которая падает, и прогоняет весь контур целиком — так гарантируется, что в
`DRY_RUN` в сеть не уходит вообще ничего.

## Файлы состояния

| Файл | Кто пишет | Что хранит |
|---|---|---|
| `seen_items.json` | NORMALIZE | хэши виденных материалов, старше 45 дней вычищаются |
| `queue.json` | QUEUE / APPROVE | посты, слоты, статусы |
| `published.json` | PUBLISH | ключи идемпотентности + журнал публикаций |
| `telegram_offset.json` | APPROVE | offset `getUpdates` |
| `analytics.json` | PUBLISH / ANALYTICS | метаданные и метрики постов |
| `rubric_weights.json` | ANALYTICS | веса рубрик для SCORE |
| `sources_health.json` | verify_sources | результат последней проверки источников |
| `leads.json` | вручную / бот заявок | обезличенные заявки, **без контактов** |
| `inbox.json` | APPROVE / INBOX | материалы владельца, результат понимания (`extracted`), отметки `processed_at` / `drafted_at` / `skipped_reason` |

Жизненный цикл статуса поста:
`draft → queued → (approved | rejected | postponed | draft) → published`.

## Расписание и бюджет Actions

| Workflow | cron (UTC) | По Дубаю | Запусков в сутки | ~мин/запуск | ~мин/мес |
|---|---|---|---|---|---|
| Collect & Generate | `0 3`, `0 12` | 07:00, 16:00 | 2 | 3–4 | ~210 |
| Approve Poll (+ inbox) | `*/30 4-18` | каждые 30 мин, 08:00–22:30 | 30 | 3–4 (+1–2, если в копилке есть новое) | ~3150 |
| Publish | `25,35 5`, `25,35 15` | 09:25/09:35, 19:25/19:35 | 4 | 2 | ~240 |
| Weekly Analytics | `0 4 * * 1` | пн 08:00 | 0,14 | 2 | ~9 |
| Verify Sources | `0 2 * * 0` | вс 06:00 | 0,14 | 4–6 | ~21 |
| **Итого** | | | **~36** | | **~3600** |

Минуты Actions округляются вверх до целой на каждый job. В каждом запуске
около 1,5 минуты уходит на служебное: checkout, setup-python и
`pip install -r requirements.txt` (в зависимостях Pillow и anthropic).
У Approve Poll к этому добавляются 90 секунд самого long-poll
(`--rounds 2 --poll-timeout 45`), поэтому запуск почти никогда не
укладывается в 2 минуты. 900 запусков опроса в месяц и дают основной счёт.

- **Публичный репозиторий — бесплатно и без лимита. Это рекомендуемый и, по
  сути, единственный бесплатный вариант при расписании по умолчанию.**
  Секретов в репозитории нет по построению, но помните, что `state/` тоже
  станет публичным: в нём не должно быть персональных данных (см. SECURITY.md).
- **Приватный репозиторий — 2000 минут в месяц на бесплатном тарифе.**
  Расписание по умолчанию (~3600 мин) в них **не укладывается**: примерно
  с 17-го числа каждого месяца workflows начнут отказываться стартовать,
  и бот тихо остановится. Варианты:
  - `*/30 4-18` → `0 4-18` (опрос раз в час) — около 2050 мин/мес,
    всё ещё на самой границе;
  - `0 4-18` плюс сокращение окна, например `0 5-16` (09:00–20:00 по Дубаю),
    — около 1500 мин/мес, это уже с запасом;
  - платный тариф GitHub.

  Цена задержки: при опросе раз в час нажатая кнопка «Опубликовать»
  срабатывает в среднем через 30 минут вместо 15.

## Как добавить новое

- **Источник** → запись в `config/sources.yml`, затем `make verify-sources`.
  `enabled: true` ставится только после `status: ok`.
- **Рубрику** → файл `prompts/<id>.md` + запись в `RUBRICS` (`pipeline/config.py`)
  + раздел в `docs/RUBRICS.md`. Тесты проверят согласованность.
- **Провайдера LLM** → класс с методом `complete(system, user, max_tokens)`
  и ветка в `get_provider()`.
- **Слот публикации** → `SLOTS` в `pipeline/postqueue.py` и cron в `publish.yml`.
