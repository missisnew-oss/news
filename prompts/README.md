# Папка `prompts/`

Промпты для генерации постов канала: один системный промпт плюс по одному файлу
на каждую рубрику. Всего 11 файлов промптов и этот README.

Промпты не захардкожены в коде: `pipeline/prompts.py` грузит их по имени
рубрики, поэтому текст можно править без единой строчки Python.

## Структура

```
prompts/
├── README.md          — этот файл
├── system_tone.md     — системный промпт: роль, tone of voice,
│                        анти-галлюцинационные правила, правовые
│                        ограничения, JSON-схема ответа
├── market_pulse.md    — Пульс рынка
├── new_launch.md      — Новый лонч
├── investor_math.md   — Считаем деньги
├── rules_and_laws.md  — Правила игры
├── area_guide.md      — Район под лупой
├── dubai_life.md      — Жизнь в Дубае
├── events_afisha.md   — Афиша
├── faq_answer.md      — Вопрос — ответ
├── case_story.md      — История клиента
└── personal.md        — Личное (генерирует БРИФ владельцу, не пост)
```

**Инвариант:** имя файла равно `rubric_id` плюс `.md`. Список `rubric_id`
зафиксирован в `pipeline/config.py` и описан в `docs/RUBRICS.md`.
Переименование файла ломает маршрутизацию; тест
`tests/test_prompts_rubrics.py` это поймает.

## Как собирается запрос к модели

```
system = содержимое prompts/system_tone.md
user   = содержимое prompts/<rubric_id>.md с подставленными плейсхолдерами
```

Системный промпт подставляется без изменений. Все переменные подставляются
в файл рубрики.

## Доступные плейсхолдеры

Подставляются кодом перед отправкой. Использовать **ровно эти имена**,
в двойных фигурных скобках, без пробелов внутри.

| Плейсхолдер | Что подставляется |
|-------------|-------------------|
| `{{items}}` | блок входной фактуры — собранные материалы в виде JSON-массива. Единственный разрешённый источник фактов и цифр. Подставляется внутрь `<INPUT_ITEMS>…</INPUT_ITEMS>`. Поля элемента: `item_id`, `source_id`, `category`, `title`, `summary`, `url`, `published_at`, `lang` |
| `{{rubric}}` | `rubric_id` текущей рубрики. Стоит в строке `RUBRIC_ID: {{rubric}}` в шапке каждого файла. Модель обязана вернуть это же значение в поле `rubric` |
| `{{rubric_title}}` | русское название рубрики из `pipeline/config.py` |
| `{{max_chars}}` | целевой лимит длины `body` для этой рубрики |
| `{{today}}` | сегодняшняя дата, формат `YYYY-MM-DD` |

Других плейсхолдеров нет. Если промпту нужна новая переменная — она сначала
добавляется в `pipeline/prompts.py::build_prompt`, потом в эту таблицу, потом
в файл рубрики.

## Обязательные элементы файла рубрики

1. Строка `RUBRIC_ID: {{rubric}}` в шапке.
2. Строки `TODAY: {{today}}` и `MAX_CHARS: {{max_chars}}`.
3. Блок входных данных ровно в виде `<INPUT_ITEMS>{{items}}</INPUT_ITEMS>`.
4. Разделы: цель поста, структура, длина, CTA, изображение, критичные
   `self_check`, чего не делать.
5. Хвост «Формат ответа — строго валидный JSON» со схемой и правилами по полям.

Если первый или третий пункт забыт, `pipeline/prompts.py` допишет их сам —
но лучше не забывать: от их места в тексте зависит, как модель читает данные.

## Контракт ответа

Модель отвечает строго валидным JSON без markdown-обёртки. Полная схема —
в конце любого файла рубрики. Ключевые правила для кода:

- `rubric` должен совпадать с переданным `{{rubric}}`.
- `length_chars` — самопосчитанная длина `body`; код проверяет её заново
  и доверяет своему значению.
- `needs_separate_text: true` — пост публикуется как подпись к фото плюс второе
  сообщение с продолжением (`pipeline/textutil.py::plan_delivery`).
- `sources` и `facts` пустые допустимы **только** для рубрики `personal`.
  Для всех остальных пустой `sources` при наличии фактических утверждений —
  брак на факт-чек-гейте.
- Любой флаг `self_check` в `false` означает, что пост не публикуется
  автоматически.
- `sources[].source_id` — идентификатор источника ровно так, как он пришёл
  в элементе `<INPUT_ITEMS>` (например `gulf_news_rss`), а не название категории.
- `sources[].url` — только из входных данных. Чужую ссылку факт-чек-гейт
  отклонит (`pipeline/factcheck.py`).
- `facts[].confidence` — `confirmed` / `single_source` / `rumour`, правила —
  в разделе «Проверка и маркировка» `system_tone.md`. `facts[].sources` —
  все url входных данных, где факт встречается. Гейт понижает `confirmed`
  без двух независимых или одного официального источника до `single_source`,
  требует маркер «по данным …» для `single_source` и не пропускает цифру из
  `rumour` без «слух / ожидается / возможно» в том же предложении. Оба поля
  необязательны для обратной совместимости, но без них гейт пишет предупреждение.

## Особый случай: `personal.md`

Единственная рубрика, где модель генерирует **не пост, а бриф для владельца**.
JSON-формат тот же, но `body` содержит текст брифа: тема, зачем каналу,
структура по абзацам, три наводящих вопроса, пример первой строки, желаемый
CTA, что НЕ писать. `sources` и `facts` — пустые массивы.

В коде эта рубрика помечена `manual: true` и исключена из автоматического
плана генерации (`pipeline/score.py::plan_rubrics`): брифы делаются отдельным
запуском, а результат идёт владелице, а не в очередь публикации.

## Как добавить новую рубрику

1. **Выбрать `rubric_id`:** латиница, строчные, `snake_case`. Id навсегда —
   он попадает в опубликованные посты, в аналитику и в deep-link лид-магнитов.
   Переименование обнуляет историю метрик по рубрике.
2. **Создать `prompts/<rubric_id>.md`** со всеми обязательными элементами.
3. **Добавить запись в `RUBRICS`** в `pipeline/config.py`: название, категории
   источников, флаг `selling`, `max_chars`, `per_4weeks`.
4. **Добавить раздел в `docs/RUBRICS.md`**: цель, формат, длина, частота,
   источники, тип изображения, пример готового поста, типичные ошибки.
5. **Пересчитать календарь** в `docs/CONTENT_CALENDAR.md`: новая рубрика
   вытесняет чей-то слот, а не добавляется сверху — ограничения «1–2 поста
   в день» и «ровно 2 личных поста в неделю» не меняются.
6. **Пересчитать долю продающего.** Если новая рубрика продвигает объект или
   услугу, она попадает в числитель, и лимит 25% проверяется заново.
7. **Прогнать `make test` и `make dry-run`.** Тесты упадут, если хоть один
   из шагов 2–5 пропущен или если доля продающего вышла за 25%.

## Правила редактирования промптов

- Общие правила (tone of voice, запрет галлюцинаций, правовые ограничения)
  живут **только** в `system_tone.md`. Не дублируйте их в файлах рубрик:
  расхождение между копиями даст непредсказуемое поведение.
- Файл рубрики описывает только то, что специфично для неё, плюс обязательный
  хвост с JSON-схемой.
- JSON-схема воспроизводится дословно и синхронизируется с валидатором
  `pipeline/llm.py::validate_payload`. При изменении схемы правятся
  `system_tone.md`, все 10 файлов рубрик и валидатор — одним коммитом.
- Формулировки про факты и цифры — не украшение: на них опирается
  `pipeline/factcheck.py`. Ослабите их — вырастет доля брака.
- Любая правка промпта проверяется прогоном `make dry-run` и, желательно,
  тестовой генерацией минимум на трёх наборах входных данных, включая набор
  с недостающей фактурой — проверка, что модель не достраивает цифры.
